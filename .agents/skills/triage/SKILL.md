# Triage

Move issues (and external PRs when `docs/agents/issue-tracker.md` enables PRs as a request surface) through the triage state machine: categorize, verify against the codebase, grill if needed, and write agent-ready briefs.

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md): writing durable agent briefs
- [AGENT-BRIEF-EXAMPLES.md](AGENT-BRIEF-EXAMPLES.md): worked examples and a counterexample
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` knowledge base rules

## Writing rules for every tracker post

- Start every posted comment or issue with:
  ```markdown
  > *This was generated by AI during triage.*
  ```
- Neutral current state only: never reproduce the reporter's words directly, name who decided, or log mission/issue history.

## Roles and state machine

- **Category (pick 1):** `bug` (broken behavior) or `enhancement` (new capability/improvement).
- **State (pick 1):** `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.
  - For PRs: `ready-for-agent` means a brief is attached for an agent to take the next step on the diff; `ready-for-human` means the owner merges.
- Every triaged item has **exactly one category and one state**. If states conflict, stop and ask the owner. Map canonical names using `docs/agents/triage-labels.md` (if missing, ask).
- Standard flow: unlabeled -> `needs-triage` -> `needs-info` | `ready-for-agent` | `ready-for-human` | `wontfix`. Reporter reply moves `needs-info` back to `needs-triage`. Flag unusual owner overrides once before applying.

## Show what needs attention

Query the tracker and present three buckets, oldest first, with counts and one-line summaries:

1. **Unlabeled** (never triaged)
2. **`needs-triage`** (in evaluation)
3. **`needs-info`** with reporter activity since the last triage notes

When PRs are in scope, include only *external* PRs (per tracker config) during discovery and tag lines `[PR]` or `[issue]`. Explicitly named PRs are always triaged regardless of author. Present the list and let the owner pick.

## Triage a specific issue or PR

1. **Gather context and check the codebase.** Read the full issue/PR body, comments, labels, prior triage notes (so resolved questions are not re-asked), and diff (for PRs). Explore using `GLOSSARY.md` and local ADRs, and run two checks:
   - **Redundancy:** search by domain concept (not reporter phrasing) to see if the behavior already exists.
   - **Prior rejection:** check `.out-of-scope/*.md` for matching rejected requests.
2. **Recommend and wait.** Give your category/state recommendation with a brief codebase summary (including whether it already exists) and wait for direction.
3. **Verify the claim.** Before grilling, reproduce a bug from the reported steps, or check out a PR and run relevant tests/commands. Report `confirmed` (with code path), `failed`, or `insufficient detail` (strong `needs-info` signal). An unverified brief sends implementation after the wrong bug.
4. **Grill if needed.** Load `grilling` and `domain-modeling` and sharpen until ready, updating `GLOSSARY.md` and ADRs inline.
5. **Apply the outcome:**
   - `ready-for-agent`: post agent brief per [AGENT-BRIEF.md](AGENT-BRIEF.md).
   - `ready-for-human`: same brief shape, naming why it cannot be delegated.
   - `needs-info`: post Triage Notes using the template below.
   - `wontfix`: close with explanation:
     - *Already implemented:* point to existing code; do **not** add to `.out-of-scope/`.
     - *Rejected bug:* plain reason, close.
     - *Rejected enhancement:* add `.out-of-scope/` entry per [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md), link it in the comment, close.
   - `needs-triage`: apply role (optional comment on partial progress).

## Quick state override

If the owner says "move #42 to ready-for-agent", skip grilling, confirm the exact label/comment/close changes, and ask whether they want an agent brief before applying.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- <settled point>

**What we still need from you (@reporter):**

- <specific, actionable question>
```

Never write vague prompts like "please provide more info"; vague questions produce another wasted round.

When the owner challenges a finding, a recommendation, or a fact, load `pushback` before you reply.
